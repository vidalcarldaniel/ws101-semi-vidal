# Skills Evidence — Matt Pocock's `skills` repository

Required skills repository: <https://github.com/mattpocock/skills>.
Cloned locally during development; the following skills were **actually
invoked** and each influence is traced to a concrete artifact below.

## Skills used

### 1. `to-spec` — turn the conversation into a spec
**Influence:** The user's request was one sentence ("productivity system, set
goals with date & time, notifies/alarm when the time meets, plus other
features"). Following the skill's process, I synthesized (no interview) a full
spec with the skill's template: Problem Statement, Solution, 24 numbered user
stories, Implementation Decisions, Testing Decisions, Out of Scope.
**Artifact:** [`docs/spec.md`](spec.md)
**Effect on the work:** The spec pinned the seam to test (the HTTP boundary)
before any code existed, and defined "alarm fires once" as an explicit user
story — which is why `notification_log` exists at all.

### 2. `domain-modeling` — build and sharpen the domain model
**Influence:** Terms were challenged and frozen before implementation:
"goal" vs "subtask" vs "alarm", the two alarm kinds (reminder vs deadline),
"active" and "overdue" defined precisely. Written to a root `GLOSSARY.md`
containing definitions only, per the skill's format rules.
**Artifact:** [`GLOSSARY.md`](../GLOSSARY.md)
**Effect on the work:** The glossary terms map 1:1 onto the schema —
`due_at`, `reminder_minutes_before`, `notification_log.kind ∈ {reminder,
deadline}`, `status ∈ {pending, in_progress, completed, cancelled}`. When the
API and UI later needed vocabulary ("active goals", "due today"), the
definitions were already settled, avoiding ad-hoc redefinitions.

### 3. `implement` — implement from the spec
**Influence:** Work proceeded strictly story-by-story from the spec at
pre-agreed seams (HTTP boundary + server actions), with typechecking run
regularly and a full build/test pass at the end, per the skill's instructions.
**Artifact:** the application source; build log in [`docs/workflow.md`](workflow.md)
**Effect on the work:** Typecheck-after-every-module caught two Next.js 16
breaking changes early (async `params`, `LayoutProps` not accepting route
groups) instead of at the end.

### 4. `diagnosing-bugs` (via the workflow) — evidence from real failures
**Influence:** Two genuine failures occurred during development and were fixed
diagnostically, not by luck:

1. **Supabase container would not start** — `bind: An attempt was made to
   access a socket in a way forbidden`. Diagnosed with
   `netsh interface ipv4 show excludedportrange`: the Windows excluded ranges
   54025–54124 and 54225–54324 covered Supabase's default ports. Fix: moved
   every port to 5532x in `supabase/config.toml`.
2. **RLS rejected a legitimate-looking insert** (42501) during API testing.
   Diagnosed as a missing `user_id` in the payload — the policy worked exactly
   as designed; the test harness was wrong. Fix: include `user_id`
   (`auth.uid() = user_id` check confirmed the DB is enforcing access control).

**Artifact:** [`docs/workflow.md`](workflow.md) — "Debugging episodes" section.

### 5. The skill that was **not** used
For honesty (the guidelines require distinguishing what a skill did and did
not do): `tdd` was **not** followed red-green-red for this build, and no
`code-review` skill session was run — the review pass was done manually (see
workflow doc). No files in this repo were generated by skills `pr`, `retro`,
`prototype`, `research`, or `to-tickets`.
